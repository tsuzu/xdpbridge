# Contributing to xdpbridge

Thanks for your interest! Issues and pull requests are welcome.

## Ground rules

* **No environment-specific data.** Do not commit real IP addresses,
  hostnames, MAC addresses, cluster names or personal identifiers. That
  includes tests, comments and examples. Use RFC 5737 addresses
  (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`) and locally
  administered MACs (`02:…`). `hack/check-hygiene.sh` enforces this in CI.
* **No secrets.** Never commit tokens, kubeconfigs or credentials.
* **License headers.** Every source file starts with an SPDX line:
  `Apache-2.0` for userspace code, scripts and manifests, and
  `(GPL-2.0-only OR BSD-2-Clause)` for files under `bpf/`.
* By contributing you agree that your contribution is licensed under the
  same terms (Apache-2.0, or the dual license for BPF sources). Please sign
  off your commits (`git commit -s`, Developer Certificate of Origin).

## Development workflow

```sh
make build              # needs clang, libbpf-dev, Go (see go.mod)
make test               # vet + gofmt + unit tests
sudo make integration   # netns integration test (root, iproute2, tcpdump, iperf3, ethtool, python3)
hack/check-hygiene.sh
```

* The BPF bindings in `internal/bpfobj/` are generated by `make generate`
  and are not committed. Regenerate them after editing `bpf/`.
* Keep `bpf/xdpbridge.h` the single source of truth for shared structs. Go types
  come from `bpf2go -type`.
* Changes to the data path should come with an integration-test case in
  `test/netns_test.sh`. Run it in both XDP modes (`--mode both`, the
  default).
* A pull request that changes `TESTLOG.md` should come from a real
  `make integration` run, not a manual edit (the summary header lives in
  `test/TESTLOG.header.md`).

## Commit messages

English, imperative mood, short subject prefixed with the area
(`bpf:`, `daemon:`, `cni:`, `flood:`, `deploy:`, `docs:`, `test:`, `ci:`),
and a body that explains *why*.

## Versioning

The project follows Semantic Versioning. Before 1.0.0, breaking changes to
the daemon API, CNI config keys or the pinned map layout are allowed in
minor releases but must be called out in the release notes.

## Releasing

Pushing a tag matching `v*` (e.g. `git tag v0.1.0 && git push origin
v0.1.0`) runs `.github/workflows/release.yml`. It builds the `Dockerfile`
for `linux/amd64`, with `VERSION` set to the tag, and pushes
`ghcr.io/tsuzu/xdpbridge:<tag>` and `:latest` using the workflow's
`GITHUB_TOKEN`. Before tagging, update the image tag in
`deploy/daemonset.yaml` to the new version.

## Reporting security issues

Please do not open a public issue for security problems. Use GitHub's
private vulnerability reporting for this repository instead.
