## Phase 2: code-side work (workstream B)

Every item below is covered by unit tests and/or the netns integration
test. The run at the bottom covers both XDP modes.

* **Fix: host on a VLAN subinterface of the uplink.** Found on real
  hardware: host ARP from `<uplink>.<vid>` never reached VLAN ports. The
  daemon now discovers the uplink's 802.1Q subinterfaces at runtime and the
  data path switches host↔port on those VLANs in both directions,
  including floods. Tests g.5–g.12 (the subinterface is created while the
  daemon runs).
* **Fix: explicit teardown.** `xdpl2-daemon teardown` refuses while a
  daemon is serving, force-detaches all pinned links, removes the pins and
  the state file, restores promiscuous mode and VLAN offloads, and
  verifies that the uplink is clean. Tests t.1–t.5 (bpftool is used to
  confirm no TCX programs remain when it is available).
* **B1: Kubernetes-API watchdog** (`--k8s-watch`, overlay
  `deploy/k8s-watch/`). Pods on the node with an xdpl2 attachment but no
  port, and ports without a pod, fail `/healthz` and set
  `xdpl2_k8s_*` gauges. Unit-tested against an httptest API server (list,
  watch, 410 relist, token rotation, API errors) and through the daemon.
  It cannot be exercised in the netns test (no API server); cluster
  validation is pending.
* **B2: `hack/validate-node.sh`.** Tests v.1–v.4 and t.5 cover local mode,
  no-bpftool fallback, remote mode through a stand-in `KUBECTL`, and
  negative cases (missing Cilium TCX programs, data path torn down).
* **B3: Distribution on Talos.** Documented in docs/design.md §11. The
  `install-cni` hostPath approach is kept, and the destination is now
  configurable (`XDPL2_CNI_BIN_DIR`). Still to be verified on the node:
  the contents of `/opt/cni/bin`, Multus `chrootDir`, and one Multus ADD/DEL.
* Status now reports the uplink's XDP/TCX programs as the kernel sees them,
  host VLANs and pins. Flood sends to a vanished port are counted as
  `tx_port_gone`, not as errors.

## Phase 1 summary

**What works (verified by the netns integration test, native and generic XDP):**

* BPF data path. The uplink XDP program switches by (MAC, VLAN) and
  passes everything else. The per-port TCX program covers pod→pod,
  pod→host, pod→LAN, VLAN tagging and anti-spoofing. The uplink TCX egress
  program covers host→pod.
* Flood path. Ring buffer hand-off and AF_PACKET replication carry ARP,
  broadcast, mDNS (224.0.0.251), SSDP (239.255.255.250) and IPv6 ND in
  every direction (LAN, host, pods). Multicast reaches joined receivers
  only, at socket level. UDP checksums of CHECKSUM_PARTIAL frames are
  finalised.
* Node daemon. Load/attach/pin, native→generic fallback, refusal to
  replace a foreign XDP program, unix-socket API, persisted state and
  restore. Unicast keeps forwarding while the daemon is down. The
  reconciler repairs drift and garbage-collects vanished ports, the
  watchdog flags unregistered veths, and `/healthz`, `/metrics` and
  structured logs are in place.
* CNI plugin. ADD/DEL/CHECK/STATUS, delegated IPAM (host-local in the
  test), loud ADD failure with full rollback when the daemon is down, and
  idempotent DEL.
* The headline macvlan regression case works: host ↔ pod and same-node
  pod ↔ pod (checks c.*, d.4, d.5, e.3).

**What is stubbed / not covered:**

* The watchdog is node-local only. It does not cross-check against the
  Kubernetes pod list (needs API access). *Addressed in phase 2.*
* Manifests are linted offline (`go test ./deploy`). kubeconform runs only in
  CI, because installing it in the devbox was not permitted. They have not
  been applied to a cluster.
* The CI integration job is written for GitHub-hosted runners (sudo, kernel
  ≥ 6.8) but has not been run on GitHub yet. Its first run must be checked.
* Throughput numbers below are veth-to-veth inside one VM. They are sanity
  checks only, not NIC performance.
* No IGMP/MLD snooping, no libxdp chaining, no per-port counters.

**What phase 2 must do:**

1. Build and push the image, then deploy to *one* labelled node with a
   native-XDP NIC (`i40e`). Check `bpftool net show` before and after
   (Cilium's TCX programs must be intact) and confirm that Cilium
   connectivity tests still pass.
2. Validate on real hardware. Check that the VLAN offload knobs actually
   turn off on `i40e` and that promiscuous mode works there. Repeat with
   one generic-mode node (`r8169` or `e1000e`).
3. Run the macvlan regression scenario on the cluster: a same-node pod and
   the host reach an xdpl2 pod's LAN IP, and an mDNS responder is
   discoverable from the LAN.
4. Verify Multus delegation end to end (thick plugin), including pod
   restarts, node reboot (bpffs pins vanish, stale registrations are
   dropped, and ports come back through CNI ADD as pods restart) and
   DaemonSet rolling updates (hitless for unicast through pinned links).
5. Add the Kubernetes-API watchdog (*done in phase 2*), run the CI workflow on GitHub and fix
   whatever the hosted runners reveal.

**Toolchain notes (devbox):**

* `bpftool` from `linux-tools-generic` is built for 6.8. The wrapper refuses
  to run on the 6.18 Talos kernel, so the versioned binary at
  `/usr/lib/linux-tools/6.8.0-*/bpftool` was used for inspection only.
  Loading and skeleton generation use cilium/ebpf `bpf2go` (Go), as allowed
  by the task. No libbpf skeletons.
* Everything else was already installed by `bootstrap.sh` (clang 18,
  libbpf-dev, Go 1.23.4, iproute2, tcpdump, iperf3, ethtool, python3), so
  `bootstrap.sh` was not changed.
* The test mounts its own private bpffs instance and does not need
  `/sys/fs/bpf`.
